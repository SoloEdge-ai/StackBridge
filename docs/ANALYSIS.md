# StackBridge 设计评估

评估日期：2026-09-17  
评估对象：`STACKBRIDGE_SPEC.md` 与 `AGENT_HANDOFF.md`

## 结论

这是一份方向成熟、风险意识较强的产品与工程基线，已经足以启动技术验证，但还不是可以直接排期交付的完整工程规格。最合理的推进方式是保留现有边界，以 M0 的四个真实垂直切片逐一消除高风险假设；在这些切片通过前，不宜先投入完整桌面壳、复杂布局或大规模业务模块。

## 设计亮点

1. **目标身份模型清晰。** `ConnectionProfile`、`ExecutionTarget` 与 `RuntimeBinding` 被明确拆分，可避免容器重建、SSH 主机变化或 UI 切换造成执行串线。
2. **终端与 Agent 执行分离。** 人工 PTY 继续保持交互语义，Agent 使用结构化执行通道，减少向当前终端盲目注入文本的风险。
3. **远端运行时职责克制。** Go runtime 只负责 PTY、文件、任务和传输，不携带模型账户或产品业务，适合远端低依赖部署。
4. **审批设计接近真实安全边界。** 审批绑定 target、binding、UID、cwd、命令、环境和文件基线，而不是只做一个通用 Allow/Deny。
5. **失败语义现实。** 对断线、取消、幂等和 unknown 状态的定义避免了不可信的 exactly-once 承诺。

## 主要风险与缺口

### 1. 范围很大，M0 仍需进一步拆票

四个 M0 原型横跨 Windows 原生依赖、WebSocket 会话、SSH、Docker、Go runtime、模型工具调用和 Codex 认证。每个原型都应独立定义成功条件、fixture、测试环境和停止条件，否则容易变成并行搭框架而没有可证实闭环。

### 2. 协议只有概念接口，缺少可生成的契约源

规格给出了 TypeScript 类型与 HTTP/WS 草案，但尚未选定权威 schema、版本协商、错误码、帧大小、背压和兼容策略。TS/Go 双端若各自手写类型，较早就会发生漂移。建议在 M0-B 前确定唯一协议源并建立契约测试。

### 3. Windows PTY 与后台生命周期是首个硬门槛

独立 Core 要跨浏览器刷新与 Electron 窗口生命周期持有 ConPTY，会遇到原生模块 ABI、进程树终止、编码、输入法、全屏程序和流控问题。这个切片应先证明会话可重连和同一 Shell 状态保持，再扩展标签、分屏和命令块。

### 4. Codex 集成必须以实测能力矩阵为准

设计正确地区分了 ChatGPT/Codex 与 OpenAI-compatible API，但 App Server、required MCP、本地内置工具隔离和审批边界需要锁定实际版本验证。任何无法证明原生工具被关闭或约束的版本，都只能开放建议模式，不能标记为托管执行可用。

### 5. 安全目标需要威胁模型和可验证策略

当前安全要求分散在各章节中。进入 M0-B/M0-C 前，应整理威胁主体、资产、信任边界、允许/拒绝矩阵和反例测试，尤其覆盖路径穿越、symlink/junction、bind mount、容器重建、主机密钥变化、operationId 重放及审批后竞态。

### 6. 产品成功指标尚未定义

规格列出了大量验收用例，但缺少可量化的体验与可靠性目标，例如终端输入延迟、持续高频输出的内存上限、断线恢复时间、日志保留预算和安装包体积。M0 测试时应记录基线，M1 前再确定目标值。

## 推荐执行顺序

1. **M0-A：Windows Web 终端。** 只做独立 Core、单 PowerShell PTY、单 Web 页面和刷新重连；先验证 node-pty/ConPTY 与生命周期。
2. **协议基础。** 选定权威 schema，定义版本、错误、事件序号、帧限制和 TS/Go 契约测试。
3. **M0-B：隔离目标 fixture。** 在本机、SSH 宿主和 Docker 容器放置同名文件，验证 binding、防串线、容器重建失效和结构化 argv。
4. **M0-C：FakeProvider 到真实 API。** 先以确定性 provider 覆盖审批与异常，再在用户提供合法档案后做一次真实流式工具调用。
5. **M0-D：Codex 可行性。** 锁定版本并记录能力矩阵；若隔离边界不成立，明确降级为建议模式。
6. **再进入 M1。** 只有 M0 证据完整后，才扩展标签、分屏、工作区、持久化和桌面打包。
